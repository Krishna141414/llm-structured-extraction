Key findings

      
    
        
  • All 7 booking emails gave valid JSON on the first try, except one that needed a retry. Greedy decoding plus one example keeps the format stable.
    • 
        
  • Validation checks structure, not truth. For the email without a guest count, the model guessed 2, and that passes the schema.
    • 
        
  • Retries fix format, not content. "SUITE" was "fixed" to "unknown". When the model got swapped dates back as an error, it repeated them on both retries.
    • 
        
  • The parser repairs cheap failures for free. Fences, chatter, trailing commas, None and truncation are fixed without another model call.
    • 
        
  • Spam is rejected explicitly through {"not_booking": true} instead of an invented booking.
    •

Honest limits

    
Limitations

    
    
      
  • Only 8 hand-written emails were evaluated. This is a demo, not a benchmark.
    • 
      
  • The 0.5B model invents plausible values (a guest count, dates on retry) that pass the schema. There is no check that values actually appear in the email.
    • 
      
  • A retry can make things worse: it may blank a value ("unknown") or copy the same mistake again.
    • 
      
  • The fallback regexes are English-only, assume DD/MM/YYYY, and resolve yearless dates against a fixed reference date (2026-10-31).
    • 
      
  • Each model call takes about 5-20 s on CPU, so a run with retries can take up to a minute.
